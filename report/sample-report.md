# Workflow QA Report: Lead intake (webhook -> LLM -> Google Sheets)

- **Report date:** 2026-10-08
- **Workflow audited:** `workflow/lead-intake.json` (4 nodes, "Lead intake - classify and log (SAMPLE, fictional)")
- **Turnaround:** written report within 48 hours of receiving the workflow export
- **Communication:** async, written only (email)
- **Method:** static review of the exported JSON + reproducible stress simulation

> **This is a public sample.** The workflow is fictional and was written for this
> repository. There is no customer, no real data and no real key (the one key in the
> JSON is a planted placeholder). Every number in this report is generated by
> `python -m n8nqa report`; the test suite fails if this file and the generated output
> differ.

## 1. Summary

- **10 findings:** 1 critical, 3 high, 5 medium, 1 low. After the fixes in `lead-intake.fixed.json`: 0 findings.
- **Scenario A: burst with redeliveries, as delivered:** 50 leads per burst, 10.0% redelivered by the sender, 5.0% of LLM calls failing, 20 seeded runs. 87.3% of leads were recorded exactly once; 85 duplicate rows were written and 42 leads were lost without any alert.
- **Same scenario with the fixes:** 100.0% recorded exactly once, 0 duplicate rows, 0 silent losses.
- **Scenario B: degraded LLM provider** (30.0% of LLM calls failing): as delivered 265 leads were lost silently; with the fixes 0 were lost silently and 21 were parked in the dead-letter sheet with an alert, ready to replay.
- **Fix first:** F1 API key stored in the workflow JSON; F2 Redelivered webhooks create duplicate rows; F3 External calls fail on the first transient error.

## 2. Findings (most severe first)

### F1 · CRITICAL · API key stored in the workflow JSON

- **Rule:** `HARDCODED_CREDENTIAL`
- **Nodes:** `Classify lead (OpenAI)`
- **Evidence:** Classify lead (OpenAI): parameters.headerParameters.parameters[0].value contains sk-EXA...(36 chars)
- **Impact:** The key ships with every export, backup and copy of this workflow; anyone with the JSON can spend on the account. It also bypasses n8n's encrypted credential store.
- **Fix:** Move the key into an n8n credential (HTTP Request -> Authentication -> Predefined Credential Type -> OpenAI) and rotate the exposed key at the provider today.

### F2 · HIGH · Redelivered webhooks create duplicate rows

- **Rule:** `NON_IDEMPOTENT_WRITE`
- **Nodes:** `Append to Leads sheet`
- **Evidence:** Append to Leads sheet: operation 'append', no dedupe key upstream
- **Impact:** Webhook senders retry on timeouts and 5xx. Every retry appends another row and pays for another LLM call; reports built on the sheet double-count.
- **Fix:** Add a Remove Duplicates node (operation 'Remove Items Processed in Previous Executions', key = the sender's event id) right after the webhook, and switch the write to 'Append or Update Row' matched on event_id. For a strict guarantee under simultaneous redeliveries, claim the key in a store with a unique constraint (Postgres INSERT ... ON CONFLICT DO NOTHING, or Redis SET NX).

### F3 · HIGH · External calls fail on the first transient error

- **Rule:** `NO_RETRY`
- **Nodes:** `Classify lead (OpenAI)`, `Append to Leads sheet`
- **Evidence:** Classify lead (OpenAI): retryOnFail not set; Append to Leads sheet: retryOnFail not set
- **Impact:** A single 429/5xx/network blip from the LLM or Google API fails the whole execution and the lead is not written.
- **Fix:** Node settings -> Retry On Fail: on, Max Tries 3, Wait Between Tries 1000 ms.

### F4 · HIGH · Failures are silent

- **Rule:** `NO_FAILURE_ALERT`
- **Evidence:** settings.errorWorkflow is empty and there is no Error Trigger node
- **Impact:** A failed execution is visible only to someone who opens the Executions list. Lost leads are discovered days later, by the sales team, not by the owner of the flow.
- **Fix:** Create a small error workflow (Error Trigger -> Slack or email with workflow name, execution URL and error message) and select it in Workflow settings -> Error Workflow.

### F5 · MEDIUM · Failed items are dropped instead of parked

- **Rule:** `NO_ERROR_BRANCH`
- **Nodes:** `Classify lead (OpenAI)`, `Append to Leads sheet`
- **Evidence:** Classify lead (OpenAI): onError = 'stopWorkflow'; Append to Leads sheet: onError = 'stopWorkflow'
- **Impact:** When retries run out the execution stops; the payload only survives in the execution log (if saving failed executions is on) and nobody replays it.
- **Fix:** Set Node settings -> On Error to 'Continue (using error output)' and route that output to a dead-letter row keyed by event_id plus an alert, so the item can be replayed.

### F6 · MEDIUM · A hung API call holds the execution open

- **Rule:** `NO_TIMEOUT`
- **Nodes:** `Classify lead (OpenAI)`
- **Evidence:** Classify lead (OpenAI): options.timeout not set; settings.executionTimeout not set
- **Impact:** A slow or hung response keeps the execution (and the webhook caller) waiting; the caller gives up and redelivers, which feeds the duplicate-row problem.
- **Fix:** Set HTTP Request -> Options -> Timeout to 30000 ms and Workflow settings -> Timeout Workflow to 120 s.

### F7 · MEDIUM · Bursts hit the LLM provider unthrottled

- **Rule:** `NO_RATE_LIMIT_GUARD`
- **Nodes:** `Classify lead (OpenAI)`
- **Evidence:** Classify lead (OpenAI): called once per webhook, no back-off or throttle
- **Impact:** Each webhook starts its own execution, so a burst of N submissions makes N parallel LLM calls. Provider 429 responses become failed executions.
- **Fix:** Retry with Wait Between Tries >= 1000 ms so 429s back off, and cap parallel executions on the instance: N8N_CONCURRENCY_PRODUCTION_LIMIT (regular mode) or the worker --concurrency flag (queue mode).

### F8 · MEDIUM · Anyone with the URL can post leads

- **Rule:** `WEBHOOK_UNAUTHENTICATED`
- **Nodes:** `Lead webhook`
- **Evidence:** Lead webhook: authentication = none
- **Impact:** Whoever learns the URL can write rows into the sheet and spend LLM tokens.
- **Fix:** Webhook -> Authentication: Header Auth with a shared secret, or verify the sender's HMAC signature in a Code node before any other step.

### F9 · MEDIUM · Model output is written without a check

- **Rule:** `LLM_OUTPUT_UNVALIDATED`
- **Nodes:** `Classify lead (OpenAI)`
- **Evidence:** Classify lead (OpenAI) -> Append to Leads sheet with no IF/Switch/Code/Filter in between
- **Impact:** Free-text model output is written as the label. An off-list answer such as 'Probably sales.' lands in the sheet and silently drops out of label-based filters.
- **Fix:** Ask for a fixed label set (JSON or enum), then add an IF/Switch that writes only allowed labels and routes anything else to the dead-letter/review path.

### F10 · LOW · Caller waits for the whole flow

- **Rule:** `SYNC_WEBHOOK_RESPONSE`
- **Nodes:** `Lead webhook`
- **Evidence:** Lead webhook: responseMode = lastNode
- **Impact:** The sender waits for LLM + sheet write before getting a response. If that exceeds the sender's timeout it retries, which multiplies duplicates.
- **Fix:** Set Webhook -> Respond to 'Immediately' (onReceived) so the sender is acknowledged before the work starts.

**What the simulation is and is not.** It replays the same deliveries and the same
failure rolls through both pipeline configs, so the difference is the pipeline, not
luck. Latency is a model (LLM attempt ~N(900, 300) ms, sheet write ~N(150, 30) ms),
useful for comparing before and after, not as a production forecast. Retries make
some leads slower (a lead that waits 1 s and retries is slower than a lead that is
dropped), which is why p95 moves. Provider rate limits (429) and concurrency caps
are not simulated; that risk is covered by the static finding.

## 5. Runbook

**What normal looks like.** The `Dead letter` sheet is empty and `#lead-intake-alerts`
is quiet. Every form submission becomes exactly one row in `Leads`, keyed by `event_id`.

**When an alert fires.**
1. Open the `Dead letter` sheet and find the row for the `event_id` in the alert.
2. Read `reason`:
   - `401` / `invalid api key` -> the OpenAI credential was revoked or rotated. Update it
     in n8n -> Credentials -> *OpenAI (credential store)*. No workflow edit needed.
   - `429` / `rate limit` -> too many parallel calls. Lower
     `N8N_CONCURRENCY_PRODUCTION_LIMIT` (or worker `--concurrency`) and replay.
   - `timeout` -> provider incident. Check the provider status page, replay later.
   - `label not allowed: ...` -> the model answered outside the label set. Label the lead
     by hand in `Leads`, or replay after tightening the prompt.
3. Replay: re-send the original `payload` from the dead-letter row to the webhook with
   the header `X-Replay: r1` (use `r2`, `r3` for later attempts). The replay header lets
   the event past the dedupe step; the upsert on `event_id` still keeps one row per lead.
4. Mark the dead-letter row `resolved` with the date.

**Changing the workflow.** Export the JSON before and after every change and keep both
in version control. Re-run the audit (`python -m n8nqa audit <file>`) and expect zero
critical/high findings before activating.

**Rotating the API key.** Create the new key, paste it into the n8n credential, run one
test submission, then revoke the old key. Keys never go into node parameters.
